# 整车移植实验：女武神 → 科迈罗 LT

**目的**：验证"记录体是纯数据、身份在描述符 key"这一结论——
把 S 级 Aston Martin Valkyre 的**全部**物理搬到 D 级 Chevrolet Camaro LT，
看它是否除了外观以外完全变成女武神。

---

## 1. 记录定位（6.0.0k）

| 车 | CarPhysics | CarChassis |
|---|---|---|
| Chevrolet Camaro LT | `0x18E38` / 428B | `0x24CD` / 156B |
| Aston Martin **Valkyre** | `0x3E84` / 428B | `0x64FB` / 149B |

> 库里拼作 **Valkyre**（少一个 i），不是 Valkyrie。
> 另有 `Aston Martin Valhala`（瓦尔哈拉）和 `LEGO_Aston_Martin_Valkirie`，
> 三者都会被模糊匹配撞上，必须用精确名。

## 2. 两种搬法

| 情况 | 手法 | 文件长度 |
|---|---|---|
| CarPhysics 428 == 428 | 记录体原地覆盖 | 不变 |
| CarChassis 156 ≠ 149 | **改描述符指向** | 不变 |

尺寸不同时本来要整库重排，但那会改变文件长度，
而 **Pegasus manifest 里记着每个 asset 的明文大小**，对不上就得连 manifest 一起改。

**改指向**绕开了整个问题：把科迈罗底盘描述符的 `off/size` 直接写成女武神那条
（记录体只读，两条描述符共享一段数据完全安全）。
**CarChassis 全库只动了 3 个字节。**

## 3. 改动量

| 库 | 长度 | 改动 | 位置 |
|---|---|---:|---|
| CarPhysics.gdb | 162,012 → 162,012 | 98 B | `0x18E4E`–`0x18F96`（全在科迈罗记录内） |
| CarChassis.gdb | 65,619 → 65,619 | 3 B | 描述符表内 |

107 个槽里 42 个变化；**91/107 与女武神原记录逐位相同**，
差的 16 个是满改把低级值抬到满级值——所以任何车库状态下都输出满级女武神。

## 4. 移植前后

| | 科迈罗原 | 移植后 |
|---|---:|---:|
| 物理极速 | 228 | **278.5**（预测 HUD ≈ 387） |
| 加速 | 1.943 | 2.400 |
| 抓地 | 0.619 | 0.828 |
| 转向锐度 | 32000 | 45600 |
| 操控 idx77 | 0.40 | 0.65 |
| 质量 | 1521 kg | 1260 kg |
| 重心高 | −0.175 | **−0.115** |
| **抬轮指数** | 0.0686 | **0.0586（更低）** |

**注意抬轮反而降了。** 抓地涨了 34%，但重心从 −0.175 提到 −0.115、
前轮距从 1.58 加宽到 1.626 —— 女武神本来就是压得极低的赛道车。
这正是拼装式调参做不到的：**原厂配平是一整套，抓地和几何互相咬合。**

氮气四级也整套搬过来（加成全面高一档、蓝喷维持 5000 → 4350），
包括决定蓝条宽度的那部分——不再是从三台不同的车拼出来的组合。

## 5. 构建

```
transplant.py --from "Aston Martin Valkyre" --to "Chevrolet Camaro LT" --with-chassis --maxed --apply
repack.py    (只替换 2 个 asset，其余 32,894 条目 CRC 全等)
apksigner sign --ks a9-repack.keystore     # build-tools 37.0.0
```

> **build-tools 35.0.0 的 apksigner 签不了 3.5GB 的包**——
> `IndexOutOfBoundsException: offset (2147683502) + size (...) > source size (...)`，
> 32 位溢出。**用 37.0.0。**

## 6. 待验证

1. 开起来是否与女武神无法区分（**这是实验的全部意义**）
2. HUD 极速是否落在 387 附近（能给换算库补第 5 个确认点）
3. 蓝条宽度是否恢复正常
