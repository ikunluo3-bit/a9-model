# 外观移植闪退诊断（6.0.0k）

结论先行：**崩在一句写死的断言上，失败的查找是 shader 参数 `powderFactor`。**

---

## 1. 崩溃现场

```
signal 11 (SIGSEGV) fault addr 0x0   Thread-342   进程存活约 90s
#00 pc 0x4bfde90  libAsphalt9.so
#01 pc 0x4bff2a0
#02 pc 0x36e209c
```

`0x4bfde90` 反汇编：

```asm
4bfde60: ldrb w8, [x0]        ; optional 的 has_value
4bfde68: cbnz w8, ->正常返回
4bfde6c: adrp x0, ...         ; "…/jtl/detail/optional/optional.inl"
4bfde7c: mov  w1, #0x23c      ; 行号 572
4bfde80: bl   assert_handler
4bfde88: mov  x8, xzr         ; x8 = 0
4bfde8c: mov  w9, #0xdead
4bfde90: str  w9, [x8]        ; *(0) = 0xDEAD ← 故意崩
```

断言文案：**`You are accessing an uninitialized optional!`**
崩溃寄存器里 `x9 = 0xdead`、`x8 = 0` 完全对得上——**不是野指针，是引擎主动求死。**

## 2. 到底在查什么

frame#2 的调用点：

```asm
36e2078: adrp x1, 0x66ed000
36e2080: add  x1, x1, #0x8dc     ; 0x66ED8DC = "powderFactor"
36e208c: bl   ...                ; 构造名字对象
36e209c: bl   0x4bff288          ; 查参数 → 空 optional → 死
```

**失败的查找就是 `powderFactor`。**
外层 `0x36e202c–0x36e2054` 是一个 for 循环：取集合长度、逐项取出、逐项调用——
**遍历这台车的每个材质，挨个要 `powderFactor` 参数。**

`powderFactor` 在 so 里与 `dirtFactor`、`texture_damage`、`diffuseTintColor`、
`deformationAmount`、`policeSiren` 挤在同一片——是**车辆 shader 参数名表**。

## 3. A/B 定位

| 版本 | 内容 | 结果 |
|---|---|---|
| v2 | 物理 + 底盘改指向 | **正常，96s 稳定运行** |
| full | v2 + manifest 改 asset_id 指向 | 闪退 |
| content | v2 + **直接换资源字节**（manifest 不动） | **同样闪退，pc 一模一样** |

**改指向和换内容结果完全一致 → 不是重复 `asset_id` 造成的索引问题，
是真正的数据不兼容。**

## 4. 不兼容在哪

模型节点/材质名对比（字符串 XOR `0xAB`）：

**女武神有、科迈罗没有：**

```
carpaint02          ← 多出来的一个材质槽
bone_anim01, detach_lip_10, detach_skirt_L/R_10, detach_wing_5
```

**科迈罗有、女武神没有（18 个）：**

```
wheelFL/FR/BL/BR_caliper                    卡钳
wheelXX_emissive_mesh_brakedisk (×4)        刹车盘自发光
emissive_mesh_brakedisk_front / rear
glass_window_B          后窗
lights_thirdlight       高位刹车灯
bone_anim_brake
detach_bumper_F_5 / _B_5 / detach_hood_60 / detach_trunk_60 / detach_wing_20
```

抽查四台车，**`carpaint02` 只有女武神有**（科迈罗、塞纳、杰AB 都没有）。

**推断**：`carpaint02` 这个额外材质由女武神自己的 CarDef 配套声明
（它的 CarDef 记录 2835 B，比科迈罗的 2694 B 多 141 B，
且多出 `tires livery 01` 与一条独立刹车动画路径）。
把女武神的网格接到科迈罗身上、CarDef 却还是科迈罗的 →
这个材质拿不到参数块 → 空 optional → 断言。

**这一步是推断，尚未实证。** 决定性验证见 §6。

## 5. CarDef 能不能一起搬

查了 CarDef 的尾部区（记录尾 `0x3BEDD0` 到计数字段 `0x41ACF4`，**376,612 B**）：

```
u32 355            记录数
每项: u64 key | u32 1 | u64 gdb_key | u32 n | n × u64 依赖 key
```

是**逐记录的依赖 key 清单**。关键性质：

> 区内 47,076 个 u64 中，**命中记录偏移的有 0 个**，命中 key 的有 705 个。

**整个尾部区只按 key 引用，不含任何记录偏移** ——
所以重排 CarDef 记录（改大小、改偏移）不会破坏它。
但受体那条依赖清单仍列着科迈罗的资源 key，**得一并换**，
清单是变长的，要连尾部区一起重建。

## 6. 下一步（两条路）

**路线 A：连 CarDef 一起搬。** 技术上通了（§5），
需要：重建 CarDef 记录区 + 重建依赖表 + 把 physics/chassis key 改回科迈罗自己的。

**路线 B：换个没有 `carpaint02` 的供体。** 塞纳、杰AB 都没有。
若换成塞纳外观一次成功，`carpaint02` 的推断即被证实，
同时也说明**大部分车之间可以直接互换外观**。

**建议先跑 B**——一次构建就能验证推断，成本远低于 A。

---

## 7. B 已跑完：`carpaint02` 推断被证伪

换成杰AB（无 `carpaint02`）做供体，**照崩，堆栈逐帧相同**。
所以 §4 那条推断是错的，`carpaint02` 无关。

**另一个教训**：我第一次自动验证只看"进程活过 112 秒"就判成功了。
车主实测才发现是**进游戏更深的地方才崩**（12:20:16，进程已跑了三分多钟）。
**"进程还在"不等于"那台车被加载过"** —— 验证必须真的走到车库/选车。

## 8. 真正的嫌疑：自带名字的资源

逐个检查被换的资源里**是否写着自己的对象名**：

| 资源 | 自带名字 |
|---|---|
| `*_car.json.jmodel` 车模 | 否 |
| `*_colShape.jcol` 碰撞 | 否 |
| `*_anim.janim` 动画 | 否 |
| `*_fx_overclocked/respawn_dyn.jmodel` | 否 |
| 贴图 / 音效 | 否 |
| **`fx_shockwave_lines_*_dyn.jmodel`** | **是** |

```
fx_shockwave_lines_camaroLT_dyn                    ← 科迈罗那份里写着这个
fx_shockwave_lines_Aston_Martin_Valkyrie_dyn       ← 女武神那份里写着这个
```

**只有冲击波 FX 模型把自己的名字写在文件内部。**
换过去之后引擎按 `fx_shockwave_lines_camaroLT_dyn` 找，里面却叫别的名字。

而且科迈罗的 `fx_overclocked` 模型里硬写着 **`Chevrolet_Camaro_LT_shockwave`** ——
又一条按名字的引用。

**佐证**：崩溃查的 `powderFactor`，在 so 的字符串表里紧挨着
`deformationAmount` / `deformationNoiseAmount` / `pulseLength` / `pulseSpeed` /
`pulseDirection` —— **整组都是冲击波 FX 的 shader 参数**，不是车漆参数。

## 9. 当前方案

跳过 `shockwave` / `fx_overclocked` / `fx_respawn` 三项，
其余（车模 + 10 张贴图 + 碰撞 + 动画 + 音效，共 14 个 asset）照搬供体。

代价：氮气冲击波特效仍是受体自己的，纯外观细节。


---

## 10. 结局

`carpaint02`、"节点子集"、"FX 自带名字" —— **三条推断全错**，杰AB 和
Fordzilla P1（严格子集）照崩。

真正的结论只有一条：**模型和 CarDef 必须一起换**。
引擎按车辆定义去遍历材质取 shader 参数，只换网格必然对不上。

完整可用的方法见 [`06-整车替换-完整方法.md`](06-整车替换-完整方法.md)。

**方法论教训**：我连续三次拿"进程还活着"当验证通过，
实际游戏卡在连接错误弹窗上，一辆车都没加载。
后来补了阴性对照（纯物理版走同一路径不崩）才让这个复现有意义。
**没有阴性对照的"通过"，等于没验证。**
