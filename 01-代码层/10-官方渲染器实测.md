# 官方渲染器实测 —— 为什么 A9 卡

对象：`A9-600300-6.0.0k-base.apk` → `lib/arm64-v8a/libAsphalt9.so`（173,235,352 B）
方法：ELF `DT_NEEDED` + `.dynsym` UNDEF 符号扫描 + 全二进制字符串搜索。
**这一份是给新游戏立项做地基用的，结论要能顶得住反问。**

---

## 1. 结论一句话

**A9 的渲染器是 GLES 3.0，没有 Vulkan，没有 compute，没有 indirect draw。**
它的卡顿不是"驱动慢"，是**每一个 draw call 都必须由 CPU 逐个提交**。

## 2. 硬证据

### 2.1 动态依赖（DT_NEEDED）

```
libGLESv2.so   libGLESv3.so   libEGL.so
libOpenSLES.so libandroid.so  liblog.so  libdl.so libc.so libm.so
```

**没有 `libvulkan.so`。**

### 2.2 运行时加载也没有

`dlopen` 走不进 DT_NEEDED，所以另查字符串。165 MB 全库：

| 字符串 | 命中 |
|---|---:|
| `libvulkan` | **0** |
| `vkCreateInstance` | **0** |
| `vkGetInstanceProcAddr` | **0** |
| `vkQueueSubmit` | **0** |
| `VK_KHR` | **0** |
| `VkDevice` | **0** |
| 对照 `glDrawElements` | 有 |
| 对照 `eglSwapBuffers` | 有 |

**零命中。不是"没启用 Vulkan"，是整个代码库里不存在 Vulkan 这条路。**

### 2.3 GLES 特性档位

导入 GL 入口 **203** 个，EGL **17** 个。按各版本的标志性入口探测：

| 版本 | 探针命中 |
|---|---|
| GLES 3.0 | **8 / 8** — `glVertexAttribDivisor` `glDrawArraysInstanced` `glMapBufferRange` `glBindVertexArray` `glGenQueries` `glInvalidateFramebuffer` `glTexStorage2D` `glBlitFramebuffer` |
| GLES 3.1 | **0 / 5** |
| GLES 3.2 | **0 / 5** |

逐项确认几个关键的：

| 入口 | 有无 | 意味着 |
|---|---|---|
| `glDrawElementsInstanced` | 有 | 有实例化，这条用上了 |
| `glDispatchCompute` | **无** | **零 compute shader**，能上 GPU 的计算全在 CPU |
| `glDrawElementsIndirect` | **无** | **无间接绘制** |
| `glMultiDrawElementsIndirectEXT` | **无** | **无 GPU 驱动的剔除/合批** |
| `glBindImageTexture` | **无** | 无 image load/store |

**它虽然链了 `libGLESv3.so`，实际用的是 GLES 3.0 那一档 —— 2012 年的特性水平。**

### 2.4 音频

`libOpenSLES.so`，`AAudio` 字符串 0 命中。**用的是 OpenSL ES，不是低延迟的 AAudio。**

---

## 3. 这解释了实测剖面

实测来源：一加 Ace 6T（SM8845 / Adreno 829）`simpleperf` 18,729 采样。

| 库 | CPU 周期占比 |
|---|---:|
| `libAsphalt9.so` | 54.77% |
| `[kernel]` | 14.66%（其中 56% 在内存管理） |
| `libGLESv2_adreno.so` | 14.45% |
| `libc.so` | 9.42%（memcpy 28.7% + mutex 27.6%） |
| `msm_kgsl.ko` | 1.91% |

`libGLESv2_adreno` + `msm_kgsl` = **16.4% 的 CPU 花在图形驱动路径上**。

**这个数字是 §2.3 的直接后果，不是巧合。**
没有 indirect draw，就没有 GPU 端剔除；每帧每个物体的绘制命令和状态切换
都要 CPU 逐条穿过 GLES 驱动的校验层。Vulkan 把这层校验挪到了创建期
（pipeline 预编译、descriptor set 预绑定），提交期近乎零成本 —— 这正是
16.4% 能被吃掉的那部分。

同理，内核 14.66% 里 56% 在内存管理（27% 清零新页、20% 遍历 VMA 红黑树）
＋ libc 的 memcpy 28.7%，对应的是 **每秒 25,156 次页分配、98 MB/s 的纹理流送**。

## 4. 帧预算：为什么 120Hz 一定守不住

- 120Hz 单帧预算 **8.33 ms**
- 实测渲染线程单次调度 **6.07 ms**（余量 2.26 ms）
- 该机 ACD（自适应时钟拉伸）热机时把有效频率压到标称的 **52%–67%**

冷机测得耗时 `T`，热机变成 `T / f`。要热机仍塞进 8.33 ms：

```
T ≤ 8.33 × f
  f = 0.52  →  T ≤ 4.33 ms
  f = 0.67  →  T ≤ 5.58 ms
```

**6.07 ms 无论按哪个 f 都超。** 这就是"锁 60Hz 一试就灵"的原因 ——
预算翻倍到 16.67 ms，`16.67 × 0.52 = 8.67 ms`，砍完仍然干得完。

> ⚠️ 数据源里 6.07 ms 一处写"平均"、图注写"99.9 分位"，两者不一致。
> 上面按**保守解**（要求尾部也塞进预算）推导，结论不受影响。

## 5. 对新游戏的意义

| 官方的做法 | 我们的做法 | 依据 |
|---|---|---|
| GLES 3.0，无 indirect draw | **Vulkan**，SRP Batcher / GPU instancing | §2.1–2.3，16.4% 驱动开销可回收 |
| 无 compute shader | compute 可用（剔除、粒子、后处理） | §2.3 |
| 98 MB/s 持续纹理流送 | **全量常驻，赛中零流送** | 见交接书 04 §场景预算 |
| 渲染 1845×838 拉到 2800×1272（43%） | 渲染倍率交给玩家 + FSR/STP | 实测 |
| OpenSL ES | AAudio | §2.4 |

**"官方优化差"这句话现在有了机制级的解释，不是感觉。**
